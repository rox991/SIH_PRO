What this console cannot do

An admin can audit that data moved and under which consent, but cannot read the clinical payload itself. The disclosures/ node grants read access only to the patient who signed the artefact and to the facility named in it — there is no admin clause. Opening a consent below shows metadata and a signature, never a diagnosis.

An admin also cannot revoke a consent. Withdrawal is a patient-only write in consents/$cid, because a platform operator forcing a withdrawal would be indistinguishable from one forging a grant.

Enforced in database.rules.json, not in this page.

ABHA Registry

Health accounts created through the Aadhaar onboarding flow, from abha/. Note what is absent: no Aadhaar number is stored anywhere in this database — only the last four digits, kept so a patient can recognise their own record.

privacy_tip
Data minimisation. The Aadhaar number the patient types is used to derive a demographic assertion in the browser and is then discarded. It is never written to the database, never sent to this console, and cannot be recovered from aadhaarLast4. Mobile numbers are stored masked for the same reason.

Linking Activity

Every attempt by a facility to attach a record to a patient's ABHA, reconstructed from the access ledger. A record only becomes fetchable after the patient approves the link and then separately signs a consent that includes it.

This view is built from dataAccessLogs/ rather than linkRequests/ on purpose: link requests carry the proposed FHIR bundle, and no admin clause exists on that node. The ledger records that a link was proposed without exposing what was inside it.
